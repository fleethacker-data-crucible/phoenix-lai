Quick Start
This API provides an OpenAI-compatible gateway for accessing enterprise LLM providers. Use your STARK API key in the Authorization header to authenticate requests. An external OpenAI account is not required.

API keys and base URLs are environment-scoped. Keys automatically lock 14 days after unlock and can be unlocked at any time in the Keys tab.
cURL
# Ensure STARK_API_KEY is exported in your environment:
# export STARK_API_KEY="your-api-key"
curl -X POST https://XXX/v1/chat/completions \
  -H "Authorization: Bearer ${STARK_API_KEY:-YOUR_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gemini-3.5-flash-lite-withtools",
    "messages": [
      {"role": "user", "content": "Hello, how are you?"}
    ]
  }'
API Reference & Capabilities
POST /v1/chat/completions

Creates a chat completion for the given messages. Compatible with OpenAI's Chat Completions API. Note: POST /v1/chat/completions and POST /v1/embeddings are active Phase 0 endpoints; the OpenAI Responses API (POST /v1/responses) is planned for Phase 3.

Assist-lane model notice: Gemini Enterprise models ending in -assist (such as gemini-3.5-flash-assist) drop system messages and ignore tool definitions. When your pipeline requires system instructions or tool calling, use a standard model (e.g. gemini-3.5-flash or alias gemini-3.5-flash-withtools).

Connect models to external tools and APIs using OpenAI-compatible function calling. Provide schema definitions in the tools array. When the model invokes a tool, execute your function locally and return the output with role: "tool" and the matching tool_call_id.

Multi-Turn Tool Calling Workflow
cURL
# Turn 1: Send user prompt along with tool definitions
curl -X POST https://XXX/v1/chat/completions \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gemini-3.5-flash-lite-withtools",
    "messages": [
      {"role": "user", "content": "What is the weather in Paris right now?"}
    ],
    "tools": [
      {
        "type": "function",
        "function": {
          "name": "get_current_weather",
          "description": "Get current weather for a specific location",
          "parameters": {
            "type": "object",
            "properties": {
              "location": {"type": "string", "description": "City and state, e.g. Paris or Tokyo"},
              "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]}
            },
            "required": ["location"]
          }
        }
      }
    ],
    "tool_choice": "auto"
  }'

# Turn 2: Submit tool execution result back to the model
curl -X POST https://XXX/v1/chat/completions \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gemini-3.5-flash-lite-withtools",
    "messages": [
      {"role": "user", "content": "What is the weather in Paris right now?"},
      {
        "role": "assistant",
        "tool_calls": [
          {
            "id": "call_123456",
            "type": "function",
            "function": {
              "name": "get_current_weather",
              "arguments": "{\"location\":\"Paris\",\"unit\":\"celsius\"}"
            }
          }
        ]
      },
      {
        "role": "tool",
        "tool_call_id": "call_123456",
        "content": "{\"temperature\": 18, \"condition\": \"Sunny\"}"
      }
    ]
  }'

Token Budget & Reasoning Guidance
Structured output generation and schema validation require sufficient token headroom. When configuring max_tokens, allocate a budget of at least 500–1,000 tokens. Constrained token budgets (<300 tokens) may exhaust the generation window during schema formatting or trigger a prose fallback response instead of valid schema-adherent JSON.

Stream responses token-by-token using Server-Sent Events (SSE) by setting stream: true. To receive complete token usage metrics at the conclusion of the stream, include stream_options: { include_usage: true } in your request payload.

Rate limits ensure fair resource distribution, protect cluster stability, and maintain multi-tenant GPU availability. The gateway meters usage across concurrent dimensions: rolling burst gates (TPM and RPM) and cumulative 24-hour credit budgets. All client-facing telemetry and quota tracking operate strictly in credits, without exposing raw dollar figures.

Rate Limit Dimensions
Dimension	Window	What It Measures & How to Handle
Tokens Per Minute (TPM)	Rolling 60s	Total prompt and completion tokens across active requests. Throttling is brief (seconds); honor the Retry-After header.
Requests Per Minute (RPM)	Rolling 60s	Total individual API calls. Space out rapid calls or add a short delay between batches.
Credit Budget (Window)	Rolling 24h	Cumulative credit allowance for your key or team. Resets as the window rolls over; submit a limit increase request if needed.
Credit Settlement Arithmetic
Credit consumption is calculated deterministically per request using model-specific integer weights:

Formula
Credits = (Input Tokens × Input Multiplier) + (Output Tokens × Output Multiplier)
Input and output multipliers are discrete integer values chosen from the set {1, 2, 5, 10, 25, 50} based on model tier and operational intensity.

Gemini Enterprise Lane: Inference routed through the Gemini Enterprise lane carries an input and output multiplier of 0 (zero credit drawdown). While exempt from daily credit drawdown, requests remain subject to cluster TPM and RPM burst protections.

Default Quota Tiers
Phased Rollout Notice: Standardized Tier 0 quotas are rolling out in phases across user cohorts. Active users are migrated first during Phase A, followed by general cutover. Accounts not yet migrated remain on their previously assigned quota limits until cutover. You can view your active limits anytime on the Dashboard.

Service Account Best Practices for Bulk Ingestion
Automated ingestion pipelines, batch scrapers, and background ETL jobs should adhere to these practices to maintain steady throughput and prevent pipeline interruptions:

Specify max_tokens explicitly: Define expected response lengths to optimize model generation time and avoid over-allocating token consumption.

Throttle client-side concurrency: Avoid unbounded parallel requests (such as Promise.all across hundreds of files). Size worker pools according to your RPM and TPM limits (e.g. 5 to 10 concurrent workers).

Configure SDK retries with exponential backoff: Standard OpenAI SDK clients (demonstrated in Quick Start above) support automatic retries with jitter and Retry-After parsing by setting max_retries=3.

Request Quota Increases Early: If your project requirements exceed default tier limits, submit a limit increase request from the Dashboard (Request Quota Increase) with your estimated TPM/RPM needs and workload justification.

Automatic Key Locking (14 Days)
As a defense-in-depth security measure, API keys automatically lock 14 days (336 hours) after creation or unlock. When a personal key is locked, API requests return an HTTP 401 Unauthorized response with a self-service unlock URL (team keys require an administrator to unlock in the portal):

JSON
{
  "error": {
    "type": "unauthorized",
    "message": "API key locked - visit the unlock URL to re-enable your key",
    "unlock_url": "https://.../unlock/<your-key-id>"
  }
}
Unlocking Your Key
Visit the unlock_url from the error response to immediately re-enable your key without generating new secrets.

Or navigate to the API Keys dashboard and click the Unlock button on the corresponding key card.

Key Expiration & Rotation Policy
API keys carry a strict lifecycle expiration date. Unlike temporary 14-day locking, an expired key is permanently decommissioned and cannot be re-enabled.

Temporary Lock vs Permanent Expiration: A locked key retains its secret token and resumes normal operation once unlocked. An expired key is invalidated across all gateway endpoints.

Zero-Downtime Rotation: Prior to key expiration, create a new API key in the portal, deploy the secret to your client application, verify incoming traffic, and revoke the legacy key.

The platform follows a structured model lifecycle to ensure stability and smooth transitions across model generations. Query GET /v1/models to dynamically inspect currently enabled models and their status for your API key.

Model Identifier Taxonomy
Endpoints use standardized model identifiers based on backend capabilities and routing lanes:

Gemini Enterprise Lane (Plain Identifiers): Plain canonical vendor identifiers (e.g. gemini-3.5-flash, gemini-2.5-flash) route to the zero-credit settlement lane for standard conversational inference.

Tool Calling & Structured Outputs (-withtools): Requests requiring function/tool calling or strict JSON schema enforcement currently require the -withtools capability suffix (e.g. gemini-3.5-flash-lite-withtools, gemini-3.5-flash-withtools).

Canonical Rename Window: The platform is transitioning toward unified canonical identifiers across all lanes. During this transition, client applications must continue using -withtools for tool calling and structured outputs until the canonical alias cutover is formally scheduled.

Embeddings: Text embeddings use canonical embedding model identifiers (e.g. gemini-embedding-2).

60-Day Alias Deprecation Window
Legacy capability suffixes (such as -withtools) undergo a strict 60-day migration window from announcement:

Active Window (Days 1 to 60): The deprecated model alias remains functional. Responses include standard warning headers (Sunset, Deprecation, and Link: <...>; rel="successor-version") encouraging clients to migrate to the canonical identifier.

Retirement (Day 61+): The alias is permanently retired and returns an HTTP 410 Gone response with a successor Link header and structured guidance payload identifying the replacement model.

HTTP / JSON
HTTP/1.1 410 Gone
Content-Type: application/json
Link: </v1/models/gemini-3.5-flash>; rel="successor-version"

{
  "error": {
    "message": "Model 'gemini-3.5-flash-withtools' was permanently retired on 2026-11-25T00:00:00Z. Please update your client configuration to use 'gemini-3.5-flash'.",
    "type": "model_retired_error",
    "param": "model",
    "code": "model_retired",
    "details": {
      "deprecated_model": "gemini-3.5-flash-withtools",

}
The API uses standard HTTP status codes to indicate the success or failure of requests.

400 Bad Request - Invalid request body or parameters

401 Unauthorized - Invalid, missing, or locked API key. Note: Direct client-side browser calls (such as fetch() or Axios) fail during CORS preflight (OPTIONS) with HTTP 401. API calls must originate from server-side applications.

403 Forbidden - API key does not have permission for this endpoint

404 Not Found - Resource or endpoint does not exist

410 Gone - Permanently retired model alias past the 60-day deprecation timeline (returns successor model payload)

429 Too Many Requests - Rate limit (TPM/RPM) or credit quota exceeded

500 Internal Server Error - Server error

502 Bad Gateway - Upstream LLM backend failure

Request Tracing (x-request-id)
Every API response returned by the platform contains a server-generated x-request-id HTTP header containing a unique UUID. Always include this ID when filing support tickets or investigating unexpected errors to allow engineers to locate relevant gateway audit logs.

bash
# Pass -i to cURL to inspect HTTP response headers:
curl -i -X POST https://stark.example.com/v1/chat/completions \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model": "gemini-3.5-flash", "messages": [{"role": "user", "content": "ping"}]}'

# HTTP/1.1 200 OK
# x-request-id: 7b3f1c24-8e12-4d92-bb50-32b0a2d5918a
